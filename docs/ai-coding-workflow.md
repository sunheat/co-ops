# AI-Assisted Coding Workflow

How this project uses AI coding assistants as a controlled engineering
process rather than unconstrained generation. This document defines the
public workflow and review expectations.

## Principles

1. AI output is a draft, not a deliverable. Nothing generated by an agent
   is considered done until a human has read the diff and run the relevant
   verification.
2. The smaller the blast radius, the more freedom the agent gets. Mock
   corpus content, examples, and docs are low risk; core logic, security
   boundaries, and provider integration are high risk.
3. Every change must leave a trace: tests, verification notes, and commit
   messages that state what the change does and what it deliberately does
   not do yet.

## What AI May Generate Freely

- Boilerplate and repetitive structure (dataclasses, builders, fixtures).
- Tests and examples for existing logic.
- Mock corpus content under `data/` (documents, tickets, runbooks, sample
  records), following the domain conventions in
  `data/mock_domain/README.md` and `docs/coding-standards.md`.
- Documentation drafts in `docs/`.

## What Requires Human Review Before Merge

- Core business logic and calculation rules (e.g. margin formulas).
- Security boundaries: authentication, secret handling, endpoint wiring.
- Provider integration: any code that talks to an external LLM or cloud
  service.
- Architecture decisions: module boundaries, import direction, dependency
  additions.

In practice this means PRs touching `packages/` internals, provider
configuration, or dependency files get a line-by-line human review, while
corpus and documentation PRs get a consistency review.

## After Every AI-Generated Change

1. Read the full diff. If any part is not understood, ask before merging.
2. Run the minimal verification:
   - Python changes: `uv run pytest` (or the targeted test file).
   - Corpus changes: consistency checks against
     `data/mock_domain/README.md` conventions; format validity (JSON
     parse, markdown structure).
3. Confirm nothing secret entered the change (grep for key-like strings
   when in doubt).
4. Commit with an English Conventional Commits message; state known
   limitations in the body when the change is deliberately partial.

## Testing Requirements

- Every feature must include a minimal test or an explicit manual
  verification note in the PR description.
- Tests must not depend on live provider credentials; provider-dependent
  paths are skipped automatically when the provider is not configured.
- Mock corpus content must be internally consistent: identifiers, venues,
  currencies, and formulas must agree across files.

## Security Rules

- API keys and credentials live only in the local `.env`, which is never
  committed. `.env.example` documents the variable names.
- Keys must never appear in code, docs, logs, commit messages, or error
  messages.
- Usage logging records token counts and estimated cost, never request
  payloads containing secrets.

## Framework and Dependency Policy

- No large framework may be introduced without a written justification
  (design note or PR description) covering: what problem it solves, what
  the hand-written alternative costs, and what lock-in it creates.
- Spikes that experiment with a dependency stay isolated (e.g. a dedicated
  example script) until the owner approves adoption.
