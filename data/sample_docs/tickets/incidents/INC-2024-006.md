# INC-2024-006 — Retry loop in Trade Reporting Converter filled disk with logs

| Field | Value |
| --- | --- |
| Incident ID | INC-2024-006 |
| Date | 2024-03-11 |
| Severity | HIGH |
| Affected Modules | Trade Reporting Converter |
| Status | CLOSED |

## Timeline

- 2024-03-11 06:40 — The Trade Reporting Converter host ran out of disk
  space and the converter process crashed. The TRC009 feed to the risk
  monitoring system stopped.
- 06:55 — Investigation found log files filling the volume. The logs were
  dominated by retry messages for broker trade messages whose master-data
  mapping failed, repeating at an abnormally high frequency.
- 07:15 — The converter was restarted. The restart cleared the in-memory
  retry queue (a Java `List`), which stopped the retries and the log
  growth; the feed resumed.
- 2024-03-12, 2024-03-13 — The same log explosion recurred twice; each
  occurrence was mitigated by a restart. The mitigation was clearly
  temporary, so a problem record was raised and assigned to a developer
  for root-cause analysis.
- 2024-03-15 — Root cause identified (see below).
- 2024-03-18 — Permanent fix deployed and verified over two business days.

## Impact

The risk monitoring system received no TRC009 messages during each outage
(the longest about 35 minutes). No corrupt regulatory messages were sent,
because the converter failed before emission rather than mid-emission.

## Root Cause

Messages whose broker or instrument master data was missing could not be
mapped and were placed in the in-memory retry list. The retry routine
iterated over that list and added still-failing messages back to the same
list, so failed entries were never removed: a retry loop without exit.

In addition, the main thread started a new retry thread every five minutes
without checking whether one was already running. After several cycles,
many threads concurrently retried the same permanently failing messages,
each writing retry log lines. Log volume grew multiplicatively until the
disk was full and the process crashed. Restarting temporarily cleared the
in-memory retry list, which is why the mitigation worked until the threads
accumulated again.

## Resolution and Follow-ups

- Fix: each retry pass copies the retry list and iterates over the
  snapshot, so messages that fail again are not appended to the collection
  being iterated; the loop now terminates per pass.
- Retry attempts per message are capped, after which the message is moved
  to a dead-letter report instead of being retried again.
- Missing master-data mappings now raise a data-quality alert so the gap
  is fixed at the source instead of being retried indefinitely.
- A disk-usage alert was added below the crash threshold, and the retry
  scheduler now starts a retry thread only when none is running.
